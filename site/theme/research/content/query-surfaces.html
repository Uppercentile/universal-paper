To learn what an agreement says about you today, you ask whoever holds it and trust the reply. This note tests another arrangement: the agreement answers for itself, and anyone can check the answer.

In brief

  • The idea. An agreement names the questions it will answer, and anyone holding it can compute the answer.
  • The proof. An answer is a trace with a fingerprint. Two parties who get the same fingerprint have the same answer.
  • The cost. Nothing is added to the language. The questions use engine calls that already exist.
  • The status. An idea with one simulated example. None of it is built into a product.
  • The parts. One experiment, one set of files to reuse, and six open questions, each on its own page.
Five words used in this note
Engine
A program that applies the rules of the language to an agreement. The repository has two, written separately.
Fingerprint
A short code computed from the exact bytes of something. Change one character and the fingerprint changes.
State fingerprint
The fingerprint of where an agreement stands after its latest accepted event.
Manifest
An optional file that lists the questions an agreement will answer.
Trace
One answer: the inputs, the state fingerprint and the verdict.

The idea

The signed agreement is the interface. A party names the questions the agreement will answer. Anyone with the bytes, or with the fingerprint plus the slice of values disclosed to them, runs an engine and gets a trace: the inputs, the state fingerprint and the verdict. A second engine on the other side recomputes the same trace.

01A party names the questions

In a short, optional file beside the agreement.

02Anyone with the bytes runs an engine

Their own copy, on their own machine.

03The engine returns a trace

Inputs, state fingerprint, verdict.

04The other side recomputes it

Equal fingerprints, same answer.

If the two fingerprints match, the answer is the same, because the bytes are the same.

No account, no vendor API and no shared database sits between the two sides.

What it adds to the language

Nothing.No Term, no Event kind and no required field.

This idea needs no new language. The file that names the questions is called a manifest. It is optional. It sits beside the agreement, it is fingerprinted with the rule the language already uses, and it can only name engine calls that already exist.

QuestionExisting engine callWhat the call reads
Is this member covered?simulate_eligibilityThe participation, its term, and the agreement it sits under
What fee is owed?derive_state (the fee derivation)The obligations of the UP:Admin-Fee clause
Would this change be accepted?simulate_amendmentThe agent’s Mandate and axiom A9, bounded delegation

An agreement with no manifest is exactly as valid as one with a manifest, and a manifest cannot change what an agreement means. Delete every manifest and every agreement still computes the same.

The manifest

The example was derived from the generative example bundle in the repository. It names three questions about one agreement, Master X. It is simulated, and no party signed it.

  1. Question 1Is this member covered by this agreement at this time?

    Runs simulate_eligibility. You supply the member and the time.

  2. Question 2What administrative fee is owed, and has it been paid?

    Runs derive_state and reads the fee clause. You supply the time.

  3. Question 3Would this fee rate be accepted if the aggregator’s agent proposed it?

    Runs simulate_amendment. You supply the rate and the time.

The party naming the questions. In this example nobody signed the manifest. If a party did, it would be the same Ed25519 signature the language uses everywhere else.

The existing engine call that answers the question. A manifest cannot define a new one.
fixed, open
The arguments the manifest pins, and the ones the asker supplies, such as the member and the time.
reads
For a call that returns a whole state, the part that answers the question.

Manifest fingerprint{{MANIFEST_FP}}

Canonical JSON (RFC 8785), then SHA-256, the rule in section 1 of the domain. The hosted engine’s hash_object and a separate script written for this note returned the same value.

The trace

An answer is a trace with three parts.

Inputs
Every argument the call was given, including the time. Agreements are named by ChainId, never by their position in someone’s file.
State
The state fingerprint of each agreement the answer read. It pins the exact history the answer rests on.
Verdict
What the engine returned: eligible or not, the fee and its status, accepted or rejected and by which rule.

The trace has a fingerprint of its own, computed the same way. Here are the three example questions, asked about March 1, 2027.

The state fingerprint is not new either. Every event already carries one as prev, the fingerprint of the state it builds on, and derive_state returns it as state_hash. If two parties name the same state fingerprint, they hold the same history, whatever else differs in their files.

Recompute it yourself

The MCP server is a convenience, not the source. It runs the reference engine for you, which is handy inside an assistant. The answer comes from the bytes. A local engine must be able to recompute every trace. An answer that only one server can produce is a claim, and this idea has no use for it.

The commands for a local server and for the reference interpreter are in Experiment 002.

With only a disclosed slice

Some values in an agreement can be sealed. Every fingerprint covers the sealed form, so a party who sees every value and a party who sees none compute the same state fingerprint. A party who holds the fingerprint plus the values disclosed to them gets a full verdict for any question those values answer. For the rest, the engine says sealed instead of guessing. See Seal in the specification.

Where this could go

The third question is a small version of something larger. It lets an outside party ask, before offering anything, whether a change would be accepted.

The hope is a future app or layer in which an agreement, and possibly a party’s profile, states to outside parties: this is what I have accepted, and this is what I will keep accepting, on these conditions, if you want to make an offer. An agent reads those acceptance states and acts on them. It makes the offer that will pass, or it skips the round trip.

None of that is built. If it is built, it belongs in an app or a layer above the language, not in the language.

To answer a named question:

  1. Fetch the manifest and check its fingerprint.
  2. Load the bundle and run validate_bundle. It names any rejected events. They are skipped, and they leave the state fingerprint unchanged.
  3. Run the call the question names, with its fixed arguments and your own open ones.
  4. Build the trace: inputs, the state fingerprint of each agreement read, and the verdict.
  5. Fingerprint the trace and compare it with the other side’s.
