How to report a vulnerability

Use GitHub’s private vulnerability reporting for the repository: open a private report. Please do not open a public issue for a vulnerability.

If you cannot use GitHub’s private reporting, email contact@uppercentile.com and ask for a private channel. Do not put the details in that first email.

A good report includes:

  • the smallest bundle or input that shows the problem;
  • which engine is affected: Python, JavaScript or both;
  • what you expected to happen.

Use hypothetical data only. Never send real agreements, real prices or private keys.

What happens next

  • We aim to acknowledge your report within 5 working days.
  • We agree a disclosure date with you.
  • We credit you in the advisory and in the changelog, unless you prefer otherwise.

What counts as a security bug

Roughly from most to least serious:

  • A forged, altered, backdated or unauthorized Event, Agreement or Mandate that an evaluator accepts.
  • Two evaluators that reach different verdicts, State hashes or derived values from the same Bundle. This breaks axiom A4.
  • A sealed value that can be recovered, or a validity check that depends on a sealed value (axiom A10).
  • A rendering that differs from what the hash commits to (axiom A8).
  • Input that makes an evaluator hang, exhaust memory or crash instead of rejecting it.
  • A weakness in the specification itself, even if both engines implement it faithfully.

Typos and ordinary bugs that do not affect validity are welcome as public issues.

Supported versions

Universal Paper is a pre-1.0 draft (UP/0.1-draft). Only the latest commit on the main branch receives fixes. Until 1.0, a security fix may change what is valid, and so change the hashes of Term definitions and examples. Such changes are called out in the changelog.

How the hosted services limit risk

  • The MCP server is read-only and stateless. It holds no keys, signs nothing, writes nothing and never reads file paths. It keeps no sessions, storage or access logs.
  • No sign-in means no credentials to steal. There are no accounts, passwords or tokens.
  • The Playground runs in your browser. It sends nothing to a server.
  • Everything is served over HTTPS.
  • The website is static. It sets no cookies and runs no third-party scripts.
  • The hosted server is locked down. Its container runs as a non-root user, holds no secrets and pins its dependency versions.

The Privacy policy describes what each service processes.

How releases and code are protected

  • Releases are signed. Version 0.1.2 on PyPI carries a signed provenance attestation that ties it to release.yml in the repository. Publishing uses trusted publishing, so there are no stored upload tokens to steal.
  • Dependencies are updated automatically. Dependabot checks the Python packages and GitHub Actions monthly.
  • Two engines are checked against each other. On every change, CI runs differential tests between the Python and JavaScript engines, plus fuzz tests, with a read-only token.

Things to know before you rely on it

  • Example keys are public. Keys and salts in the examples are derived from public seeds so the examples can be reproduced. They are not secret and must never be used for anything real. Real keys and salts must be random.
  • The Playground is a demonstration, not a wallet. Do not use it to sign with real keys.
  • The JavaScript Ed25519 code is written for clarity and is not constant-time. It is fine for verifying public data, and should not be used to sign with real keys.
